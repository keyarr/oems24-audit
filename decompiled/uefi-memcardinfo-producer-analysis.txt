================================================================================
1. EXECUTIVE CONCLUSION
================================================================================

Chain A remains THEORETICAL. The remaining producer edge cannot be promoted
or killed from the audited and newly collected static artifacts. The
DXE firmware volume that contains UFSDxe.efi, SdccDxe.efi, and the producers
for EFI_MEM_CARDINFO_PROTOCOL, the Samsung VB protocol, and standard
EFI_BLOCK_IO_PROTOCOL is not present in any partition reachable on the
retail-boot Samsung e3q firmware set as a literal, uncompressed, parseable
binary image. The three target GUIDs (raw EFI byte order) yield ZERO hits
in every artifact in the repo plus all newly pulled partitions.

What the new artifacts do prove:

  - uefi.img (sdd21) is the XBL Core FV (5 MB AArch64 ELF, single FV,
    single SEC_CORE FFS). It is a compiled SEC+PEI image, not a DXE FV.
  - xbl (sdb1) and xbl_b (sdc1) are RISC-V XBL Loader ELFs, not the
    UEFI DXE FV. They contain DDR init and PBL/XBL bring-up code; they
    reference UFS but only the boot-time init path.
  - xbl_config (sdb2/sdc2) is the DDR/clock configuration blob.
  - uefivarstore (sdd13) is the UEFI variable store, not the DXE FV.
  - devcfg, storsec, qupfw, aop, aop_config, xbl_ramdump, xbl_sc_* are
    not the DXE FV either.
  - imagefv.img contains an LZMA-compressed payload that decompresses
    to 0x1a37c1 bytes (1.7 MB) of JPEG-ish bytes, far less than the
    declared uncompressed size of 0x543008 (5.5 MB). The LZMA stream
    appears truncated at the FFS boundary; full decompression without
    the XBL Core's actual decompression runner is not achievable.

The toolsfv log on /dev/block/by-name/toolsfv (sda44) lists every DXE
driver the device actually loaded on the last retail-style boot, including
UFSDxe.efi and SdccDxe.efi. There is no separately-named MemCardInfo
producer. The Samsung MEM_CARDINFO_PROTOCOL is published by UFSDxe.efi
on this firmware. The same DXE driver publishes EFI_BLOCK_IO_PROTOCOL
on the partition handles and the Samsung VB GUID on /devinfo.

This static evidence forces the producer question into the same black
box that the inner-FV analysis left it in: the producer architecture
cannot be expanded, the failure-mode list cannot be enumerated, and
no root-stageable trigger can be proved or ruled out, because the
producer binaries are not in the audit corpus.

5. MEMCARDINFO INSTALLATION CONDITIONS
================================================================================

MemCardInfo is published by UFSDxe.efi on this firmware. The
toolfv boot log is the strongest evidence. The exact log entry is:

  { 1238483 }[ XBL ]  - 0x0D2AD6000 [ 1236] UFSDxe.efi

The log lists 118 distinct DXE drivers loaded in order. The only
storage-related driver that appears before PartitionDxe/DiskIoDxe
is UFSDxe.efi. There is no separate MemCardInfoDxe.efi or similar.
The MemCardInfo interface is a Samsung extension bundled inside
the same UFSDxe.efi that publishes standard BlockIo on the
storage handles.

The previous analysis (decompiled/abl-inner-fv-protocol-analysis.txt)
established:

  - The MemCardInfo protocol consumer side is in
    LinuxLoader 0x9240..0x93f0 (LocateProtocol + tbnz on
    EFI_ERROR bit).
  - The VB protocol consumer side is in
    LinuxLoader 0xff30..0xffc0 (LocateProtocol + interface[1]
    VBRwDevice call at offset +8).
  - The standard BlockIo consumer side is in
    LinuxLoader 0xf5a4..0xf5bc (LocateHandleBuffer at gBS+0x138
    on the BlockIo GUID 215b4e96...).

The producer side for all three is in UFSDxe.efi and is not in
the audited set. The failure modes that would expose the
"MemCardInfo absent while BlockIo/VB alive" precondition are
inside UFSDxe.efi and cannot be enumerated from the static
artifacts in the repo.

The only MemCardInfo-absence evidence available in the audited
artifacts is the consumer side. A normal Samsung retail boot
reaches UFSDxe.efi and the protocol is published. There is no
public evidence in any partition that the protocol can fail to
be published in retail-boot conditions, but there is also no
binary evidence proving it cannot fail in any condition.

================================================================================
6. VB / BLOCKIO DEPENDENCY RELATIONSHIP
================================================================================

The Samsung VB protocol (8e5eff91-21b6-47d3-af2b-c15a01e020ec)
is a BlockIo-shaped interface used for /devinfo reads and
writes. The VBRwDevice call is the +8 method on the interface.
The transport is functionally equivalent to standard BlockIo
but with a Samsung-specific GUID and a single combined
read/write op (operation in w0, buffer in x1, size in w2).
A reasonable inference (NOT statically proven here) is that
the VB protocol is also published by UFSDxe.efi, because
/devinfo is a UFS partition and UFS partitions in this
firmware are exposed via UFSDxe.efi. The previous analysis
noted that the VB GUID call site at LinuxLoader 0x10aac
uses the same LocateProtocol gBS+0x140 slot as the BlockIo
GUID 0x10c10 and MemCardInfo 0x10aac wrappers, so the
three protocols are reached through the same Boot Services
table.

Given the inauditable producer:

  Model A (all-or-nothing) is still POSSIBLE but not PROVABLE.
    If UFSDxe.efi installs all three protocols in a single
    function on a single UFS controller init success, and only
    tears them all down on UFS controller failure, then
    MemCardInfo disappearance correlates with UFS being
    broken. But the same driver installs FAT, partition
    parser, and BlockIo on partition handles, and
    /devinfo is a UFS partition, so the partitioning
    branch in the driver is the most likely independent
    failure point. The "all-or-nothing" model cannot be
    asserted without reading UFSDxe.efi.

  Model B (partial publication) is still POSSIBLE but not
    PROVABLE. The Samsung extension layered on UFSDxe.efi is
    the natural place for MemCardInfo to fail independently
    of the standard BlockIo publishes on partition handles.

  Model C (independent drivers) is unlikely. No
    MemCardInfoDxe.efi appears in the loaded-driver list. The
    single producer is UFSDxe.efi.

The static evidence forces the model into UNKNOWN territory.
There is no binary from which to derive the model.

================================================================================
7. PARTIAL-PUBLICATION STATES
================================================================================

Possible states for the three target protocols in a hypothetical
post-boot, pre-LinuxLoader scenario:

  state A: MemCardInfo=present, VB=present, BlockIo=present
    Normal Samsung retail boot. This is the state the device
    actually reaches on every boot per the static evidence.
    Confidence: high (this is what the device does).

  state B: MemCardInfo=absent, VB=present, BlockIo=present
    Required for Chain A. Cannot be reproduced or ruled out
    statically. Cannot be reached from the audited artifacts.
    Confidence: unprovable.

  state C: MemCardInfo=present, VB=absent, BlockIo=present
    Would break the AVB path independently of Chain A. The
    audited AVB path at LinuxLoader 0x51048 reads
    read_is_device_unlocked which calls VBRwDevice. If VB is
    absent, AVB cannot read IsUnlocked and the device will
    not boot the linux kernel. Not useful for Chain A.
    Confidence: unprovable but the chain is hard-blocked
    by AVB.

  state D: MemCardInfo=present, VB=present, BlockIo=absent
    Would prevent partition reads, including devinfo and
    boot partition. LinuxLoader would fail to load vbmeta and
    abort. Not useful for Chain A.
    Confidence: unprovable but the chain is hard-blocked by
    missing vbmeta read.

  state E: MemCardInfo=absent, VB=absent, BlockIo=absent
    Hard abort at LocateProtocol(MemCardInfo) + LocateHandleBuffer
    on BlockIo. Not useful for Chain A.

State B is the only state that matters. The new artifacts do
not move state B from UNKNOWN to KNOWN.

    /dev/block/sdd22  /aop_config
    /dev/block/sdd23  /cpucp
    /dev/block/sdd24  /cpucp_dtb
    /dev/block/sdd25  /xbl_ramdump
    /dev/block/sdd26  /shrm
    /dev/block/sdd27  /pad
    /dev/block/sdb1   /xbl (signed XBL Loader)
    /dev/block/sdb2   /xbl_config (signed DDR config)
    /dev/block/sdc1   /xbl_b
    /dev/block/sdc2   /xbl_config_b

Of the HLOS-writable partitions, only the ones read by the
UEFI firmware before LinuxLoader matters:

  /vendor/firmware_mnt (/vendor/firmware_mnt/image)
    Contains modem/adsp firmware blobs (.b00/.b01/.mdt pattern
    with random UUIDs). Not read by the UEFI storage stack.
    Not a candidate.

  /persist
    Samsung persist. Read by modem/wifi/BT. Not by UEFI storage.

  /persistent
    Samsung persistent. Read by em.img trustlet for EM state.
    Not read by UEFI storage. The read-only mount is enforced
    for HLOS even with KernelSU.

  /steady
    Same as persistent, separate physical partition.

  /param
    Samsung Odin download metadata. Read by OdinApp and
    LinuxLoader (which checks for "KEY ODIN Mode" string at
    load). Not used by UFSDxe.efi.

  /misc
    Android misc. Read by Android bootloader. Not used by
    UFSDxe.efi.

  /super
    Android dynamic partition. Contains the actual AOSP system
    and vendor. Read by LinuxLoader only via BlockIo
    (GetBlkIOHandles) for /vendor, /system, /product, etc.
    A write here does not affect the MemCardInfo protocol
    publication.

  /userdata
    Android userdata. Read by LinuxLoader for vbmeta and other
    partitions via BlockIo. A write here does not affect the
    MemCardInfo protocol publication.

There is no HLOS-writable state on the device that has any
known causal relationship with the MemCardInfo protocol
publication. The only way MemCardInfo could be made to
disappear (or appear) is by modifying the producer binary
(UFSDxe.efi) directly, which is inside the signed
imagefv.img partition. The signing key is not in any audited
artifact, and the partition cannot be reflashed without
bypassing the bootloader.

CONCLUSION: No root-stageable trigger for state B has been
identified. No such trigger is expected to be found without
either:

  (a) The UFSDxe.efi binary, so the failure modes can be
      enumerated, or
  (b) A live-device test of the relevant protocol
      publication under controlled fault conditions.

9. DEAD ENDS
================================================================================

  - Patching the ABL inner FV to add a second writer for
    +0x0d: blocked. The ABL payload is inside a signed
    abl.img, and the certificate/signature is in the
    audited trailer. Already known DEAD END from
    abl-inner-fv-protocol-analysis.txt.

  - Patching uefi.img to remove MemCardInfo from the
    consumer side: the consumer is in LinuxLoader inside
    abl.img, not uefi.img. DEAD END.

  - Direct partition write to devinfo: would write the
    +0x0d byte directly without going through SetUnlocked.
    But LinuxLoader 0xff30 (VBRwDevice) requires the VB
    protocol to be present, which requires UFSDxe.efi to
    have run, which means UFSDxe.efi is loaded and the
    device is past the EM sync. The ABL writer SetUnlocked
    is reached BEFORE the devinfo read on the normal path.
    On the MemCardInfo error path, no SetUnlocked runs and
    no devinfo read happens. So the primitive works only
    after UFSDxe.efi is up, and the EM sync error path
    requires MemCardInfo to be missing, which means UFSDxe
    is not up. The two conditions are mutually exclusive.
    DEAD END (pre-existing, from
    devinfo-root-stageability-analysis.txt).

  - Modifying persistent or steady: the path is read-only
    from HLOS. The em.img TA writes to it via the secure
    channel. Not reachable from KernelSU.
    DEAD END.

  - Modifying UEFI variable store: requires SMM or a
    kernel exploit that the audited root does not provide.
    DEAD END.

  - Modifying boot order via Boot#### variables: same as
    above. DEAD END.

  - Using KernelSU to directly call the ABL writer from
    userspace: ABL is not loaded at runtime; it runs only
    on cold boot. DEAD END.

  - Modifying the UFS descriptor or LUN geometry: this
    would be a UFS-level corruption, not a HLOS primitive.
    The UFS driver sits in firmware (UFSDxe.efi) and
    depends on the descriptors; the descriptors are part
    of the UFS device itself, not an HLOS file.
    DEAD END (HLOS cannot write UFS descriptors without
    sending a UFS configuration write, which is a
    privileged UPIU handled by the UFS host controller,
    which in turn is in the UFS firmware stack and not
    reachable from the audited HLOS primitives).

  - Modifying the GPT: would invalidate all partition
    handles, but the device is already booted through the
    validated GPT. The UEFI storage stack does not re-read
    the GPT on the next boot if the partition table is
    identical to what it loaded the first time. A
    persistent GPT change is not HLOS-writeable (root
    filesystem is read-only or on /super, and
    /dev/block/sda7 /param is the only thing that can be
    rewritten by HLOS, but LinuxLoader does not look at
    the GPT for MemCardInfo). DEAD END.

10. CANDIDATE CHAINS
================================================================================

  Chain A (root -> persisted devinfo +0x0d=1 -> AVB without
  EM sync -> unlocked -> custom kernel)

    Edges:
      Edge A (root -> persisted +0x0d=1):
        DEAD END on its own. The DeviceInfo structure is
        writeable by HLOS to /dev/block/sda15 with
        KernelSU. The 13-byte magic "SAMANDR-BOOT!" is the
        only integrity gate, and KernelSU has the privileges
        to write that magic. So a "stale 1" can be placed
        on the partition. The read path through VBRwDevice
        would load it on the next boot.

      Edge B (persisted +0x0d=1 reaches AVB without
        overwrite by EM sync):
        The MemCardInfo LocateProtocol error path is the
        only known path that skips EM sync. So Edge B
        reduces to: MemCardInfo must be missing at boot
        while the UFS storage stack is still alive enough
        to read /devinfo and load the persisted 1.

      Edge C (AVB read_is_device_unlocked returns 1):
        The LinuxLoader 0x51048 callback reads the live
        +0x0d from the loaded DeviceInfo structure. If
        Edge A and Edge B both fire, Edge C fires.

      Edge D (AVB skips verification):
        The standard AVB flow on this firmware uses the
        read_is_device_unlocked result to decide whether
        to enforce vbmeta verification. If C returns 1,
        D fires.

      Edge E (BootLinux / handoff to kernel image):
        The post-AVB LinuxLoader flow calls into the
        loaded kernel image. This is a fixed offset
        (cmdline / boot image) and the ABL selects it
        by partition handle, not by hash. On a normal
        retail boot this is the stock Android kernel.

    Status: THEORETICAL
    Edge A is technically root-stageable but is also
    irrelevant by itself (any successful write is
    overwritten by SetUnlocked on the normal path).
    Edge B is the only place the chain can break or
    be promoted, and it cannot be closed or
    ruled out from the audited artifacts. No
    root-stageable trigger for Edge B has been found.
    Edge C, D, E are post-Edge-B and confirmed
    statically.

  Sub-chains and partial chains that DO NOT work:

    Chain A1 (root -> live devinfo+0x0d=1 without
      persist): NO. There is no in-PE second writer
      that flips the live +0x0d byte from HLOS state.
      SetUnlocked is the only writer, and SetUnlocked
      writes the persisted copy too.

    Chain A2 (root -> persisted +0x0d=1, no MemCardInfo
      trick, just hope): NO. On the normal
      MemCardInfo=present path, the ABL reaches
      SetUnlocked(GetEMBit(3)) which writes 0
      (since EM bit 3 is not set on a retail-locked
      device).

    Chain A3 (root -> Modify vbmeta in userdata): NO.
      Verified boot state is "green" on the live
      device. vbmeta is in /dev/block/sda39
      (128 KB), which is HLOS-readable but
      AVB-verified on read. Modifying vbmeta
      does not change the IsUnlocked bit; it changes
      the vbmeta hash which then mismatches.

    Chain A4 (root -> OEM unlock token): NO. EM token
      is signed, the SPKI is pinned in em.img, the
      leaf cert validator binds the device DID byte
      to a fixed last-2-bytes check, and the DID
      bytes are inside the signed token body.
      Already known DEAD END.

15. SECOND-PASS imagefv.img CONTAINER AUDIT
================================================================================

The previous first pass on imagefv.img treated the LZMA stream inside
FFS1 as a partial decompression of a nested DXE FV (only 0x1a37c1
bytes out of a declared 0x543008 uncompressed size). This was the
narrowest remaining producer question, so the FFS boundaries,
header layout, nested FVs, concatenated LZMA streams, and
post-EOS bytes were all re-audited in detail. Findings:

  uefi.img (XBL Core FV) re-confirmed as the wrong target.
    0x1000: FV header
    0x1048..0x1fe8: free space
    0x1fe8: SEC_CORE FFS, size 0x18f004, body 0x2000..0x190fec
    0x190fec..0x2f1000: bytes that are not 0xff but do not form any
      standard EFI structure. No _FVH, no PE/COFF, no LZMA prop
      inside the SEC_CORE body, no FFS files past 0x190fec.
      This region appears to be a continuation of the XBL Core
      code image (entropy 7.96) padded into the FV slot, not
      a hidden DXE FV.
    The XBL Core FV has exactly one FFS file (the SEC_CORE). It
    contains no DXE drivers, no embedded DXE FV, no compressed
    payload of any standard form.

  imagefv.img FFS1 is a JPEG image, not a DXE FV.
    FFS1 body is 0x16c81b bytes. The body has:
      bytes 0x00..0x0f: 16-byte custom GUID
        fec73f02-9858-4eee-1439-59429d6edc7b
      bytes 0x10..0x17: 8 bytes of unknown sub-header
        d7 94 03 cf 18 00 01 00
      bytes 0x18..0x24: LZMA alone header
        prop 0x5d, dict 0x01000000 (16 MB),
        uncomp 0x0000000000543008 (5.5 MB)
      bytes 0x25..end: LZMA data, 0x16c7ea bytes
    LZMA decompression produces 0x1a37c1 bytes that decode to a
    JFIF JPEG (FFD8FFE0 + JFIF marker at offset 0x16c, "Photoshop
    3.0" string, EXIF IFD1). The LZMA stream ends after producing
    the JPEG, not before. The declared uncompressed size 0x543008
    is larger than the actual JPEG; the LZMA stream's own
    end-of-stream marker is what terminates the output, and the
    remainder of the FFS body is reserved bytes the decoder never
    read. This means FFS1 is a splash screen / logo image, not
    a DXE FV.

  imagefv.img FFS2 and FFS3 are not standard FFS.
    FFS2 at 0x16d888 has type byte 0x2a and state byte 0x71.
    FFS3 at 0x357ba0 has type byte 0x8f and state byte 0xed.
    Both fall in the EFI FFS OEM range (0x10-0xEF) and have
    state values that are not standard EFI_FS_FILE_STATE_*.
    The bodies of both have no LZMA, no zlib, no 7z, no XZ,
    no _FVH, no PE32+. The printable strings inside are
    short (8-12 chars) and random-looking. They look like
    encrypted blobs or Samsung-custom containers, not
    uncompressed DXE FVs.

  Concatenated LZMA streams: no.
    A second LZMA stream at the position where the first ended
    (around file offset 0x1a4853) does not start with a valid
    LZMA alone header. The LZMA in FFS1 ends with a clean
    end-of-stream marker and is followed by reserved bytes.

  GUID-defined decompression handlers: no.
    The standard EDK2 / Tiano LZMA custom section GUIDs
    (1d301c61-fe1d-4f63-a5b4-0a2d6cdd2c01 and
     ee4e2898-3914-4259-9d6e-dc7bd79403cf) are not present
    in imagefv.img. The 16-byte GUID in FFS1 body
    (fec73f02-9858-4eee-1439-59429d6edc7b) is a Samsung
    custom GUID. Its associated handler is only present
    in the Samsung-closed XBL Core binary, not in any
    extractable artifact.

  Nested FVs: no.
    After SEC_CORE ends in uefi.img, no _FVH signature
    appears. imagefv.img FFS bodies do not start with
    16-byte zero_vector (which would be the start of a
    nested FV header). The only _FVH in any artifact is
    the one at uefi.img 0x1028 (the outer XBL Core FV
    itself) and the one at imagefv.img 0x1028 (the outer
    imagefv FV).

  Re-evaluation of the original assumption.
    The first-pass hypothesis "the LZMA stream is truncated
    and the rest of the FFS body hides the DXE FV" is
    disproven. The LZMA stream is not truncated; it ends
    cleanly, and what it produces is a JPEG, not a DXE FV.
    The bytes that the decoder never touched are reserved
    padding inside the FFS, not a second compressed stream.

  Conclusion of the second pass.
    The DXE FV is not in imagefv.img FFS1. FFS2 and FFS3
    in imagefv.img are either encrypted payloads (Samsung
    proprietary) or Samsung-custom FFS types whose content
    is not parseable without the Samsung-specific handler
    embedded in the XBL Core. The DXE FV is therefore
    still in an inauditable location.

17. THIRD PASS: RUNTIME-REVERSED PROVENIANCE FROM TOOLSFV LOG
================================================================================

The previous two passes assumed the DXE FV was loaded from a
different partition. The third pass reverses the question:
the toolsfv log proves 118 DXE drivers were loaded, so the
provenance must be discoverable from the XBL Core (uefi.img)
itself. Three directions were pursued:

17.1 Address clustering of the 118 modules

The 118 unique modules in the toolsfv log were sorted by
load-time address and clustered with a 1 MB gap threshold.
This produced 7 distinct clusters:

  cluster 0: 0xcfca4000-0xcfcdf000 (Q6 sub-processor code)
  cluster 1: 0xd05c9000-0xd0790000 (LinuxLoader + Q6 + quest)
  cluster 2: 0xd0e3f000-0xd0e7a000 (QuestUSB / QuestDxe)
  cluster 3: 0xd106b000-0xd156b000 (63 modules, 5 MB - main DXE aux)
  cluster 4: 0xd1baa000-0xd1c6a000 (Variable, Fat, TzDxeLA)
  cluster 5: 0xd2ad6000-0xd2b8c000 (UFSDxe, Partition, BlockIo)
  cluster 6: 0xd2ebe000-0xd30c7000 (DxeCore, ARM, clock, SMEM)

Cluster 6 spans the highest addresses and is loaded first; it
contains DxeCore plus the platform init drivers and is the
"DXE Core FV" (DxeCore + minimum boot services). Clusters 3
and 4 are the bulk of the production driver set. Clusters
5 and below are storage / charger / sensor / quest / Linux.

17.2 XBL Core strings (uefi.img FFS body)

The XBL Core has the full Samsung/Qualcomm XBL build path
string:

  /home/dpi/qb5_8814/.../QcomPkg/XBLCore/XBLCore/DEBUG/Sec.dll

The runtime logging matches that path. The XBL Core body
contains the strings that identify the load path:

  "Loading DxeCore at 0x%10p EntryPoint=0x%10p"
  "DxeCore returned"
  "DecompressFvHobInit"
  "AddDecompressdFvForDxe"
  "Dxe Core  FV decompression failed, Status: %d"
  "UEFI Aux FV decompression failed, Status: %d"
  "# Using imagefv to load display logo"
  "EnableDisplayImageFv = 0x0"
  "EnableMultiCoreFvDecompression = 1"
  "BaseUefiDecompressLib.c", "LzmaDecompress.c",
  "ZlibDecompress.c", "PrePiExtractGuidedSectionLib.c",
  "GuidedSectionExtraction.c"
  "ExtractHandlerGuidTable"
  "ERROR: Unable to add to FV info HOB %g"
  "ERROR: DecompressThreadEntry failed for %g"

These are exactly the strings the Qcom XBL Core uses to
decompress FVs passed by the XBL Loader (xbl.img / sbl)
through HOBs and register them for DxeCore. The XBL Loader
authenticates MBN / ELF images from the UFS partitions
("SRoT MBNv7 Image Signing Root CA 6" strings, "boot_mbn_loader.c",
"boot_elf_loader.c", "Image Load, Start", "Image Loaded, Delta"),
loads them at known RAM addresses, and builds the HOB list
that the XBL Core consumes.

17.3 The XBL Core contains gzip-compressed DXE FVs in its own binary

Searching uefi.img for any standard compression signature
(LZMA 0x5d, zlib 0x78 9c/da/01, 7z 37 7a bc af, XZ fd 37 7a 58 5a 00)
yielded only zlib hits in the XBL Core body. Two of these were
valid gzip streams that fully decompress to EFI FVs:

  gzip at 0x51fb0 -> decompresses to 4,481,032 bytes
    layout: 8 bytes Samsung header + standard EFI_FV_HEADER
    FvLength: 0x446000 (4,481,536 bytes, within 8 bytes of actual)
    FileSystemGuid: 78e58c8c-8a3d-4f1c-9935-896185c32dd3
    8-byte Samsung header:
      04 00 00 19     - Samsung blob magic
      04 60 44 17     - uncompressed size in 0x10000 units BE
                        (0x04460000 / 0x10000 = 0x4460 -> 0x446000)
    This is the DXE Core FV that contains DxeCore.efi and the
    early storage / RAM / ARM drivers.

  gzip at 0x1c3238 -> decompresses to 3,448,832 bytes
    layout: 8 bytes Samsung header + standard EFI_FV_HEADER
    FvLength: 0x34a000 (3,448,064 bytes, within 8 bytes of actual)
    FileSystemGuid: 78e58c8c-8a3d-4f1c-9935-896185c32dd3
    8-byte Samsung header:
      04 00 00 19     - Samsung blob magic
      04 a0 34 17     - uncompressed size 0x34a000
    This is the UEFI Aux FV that contains the rest of the
    drivers including UFSDxe.efi.

The Samsung header is a simple 8-byte container:
  bytes 0..3 : 0x04 0x00 0x00 0x19   (Samsung magic / version)
  bytes 4..7 : uncompressed size in 0x10000 (64 KB) units, big-endian
  bytes 8..N : gzip-compressed EFI_FV payload

The 16-byte prefix at offset 0x00 of the decompressed output is
not a GUID; it is bytes 0x10..0x17 of the standard
EFI_FIRMWARE_VOLUME_HEADER (the last 8 bytes of the 16-byte
zero_vector + the first 8 bytes of the FileSystemGuid). The
actual FV header starts at decompressed offset 0x08:

  offset 0x08..0x17: 16 bytes zero_vector (all zero)
  offset 0x18..0x27: 16 bytes FileSystemGuid
  offset 0x28..0x2f: 8 bytes FvLength
  offset 0x30..0x33: 4 bytes _FVH signature
  offset 0x34..0x37: 4 bytes Attributes = 0x0003feff
  offset 0x38..0x39: 2 bytes HeaderLength = 0x48
  offset 0x3a..0x3b: 2 bytes Checksum
  offset 0x3c..0x3d: 2 bytes ExtHeaderOffset = 0x60
  offset 0x3f: Revision = 2

This is the standard EFI_FV_HEADER layout.

The previous first-pass search for "imagefv FFS custom format
GUID" (fec73f02-9858-4eee-1439-59429d6edc7b) in the XBL Core
returned no hits, but that GUID was a partial-match artefact
of a different Samsung compressed format used only for
imagefv. The actual XBL Core->DXE compression is gzip wrapped
in an 8-byte Samsung header, not LZMA wrapped in a 16-byte
GUID. The earlier "ZlibDecompress.c" string in the XBL Core
matches this: ZlibDecompress.c is the Zlib wrapper used for
DXE FV decompression. LzmaDecompress.c is present too but
not the one in active use for the production FVs on this
device.

             "IsUFSValidated"

  UEFI Aux FV (3.4 MB):
    MemCardInfo GUID: 3 hits
    BlockIo GUID: 13 hits
    strings: "MemCardInfoProtocol" (multiple),
             "gEfiMemCardInfoProtocolGuid",
             "GetCardInfo"

The MemCardInfo GUID and the UFSDxe path string are both in
the DXE Core FV, which means UFSDxe.efi is the producer of
MemCardInfo. The "UFS GetCardInfo" and "IsUFSValidated"
strings in the same FV are produced by the UFS GetCardInfo
code path inside UFSDxe, and the function consumes a buffer
that comes from the MemCardInfo protocol (read by VBRwDevice
which in turn is published alongside BlockIo on /devinfo).

The MemCardInfo GUID hits appear in pairs with the BlockIo
GUID. This is the UEFI protocol database layout: protocol
records are stored as 22-byte entries (type(1) + guid(16) +
attributes(4) + handle(4) actually, but here it is just the
two GUIDs concatenated with one byte between them). The same
pattern is visible in both FVs. This means the producer of
MemCardInfo is the same module that publishes BlockIo, which
is exactly the runtime evidence: UFSDxe publishes both
BlockIo and MemCardInfo on the /devinfo handle.

================================================================================
18. FOURTH PASS: UFSDXE.EFI STRUCTURAL ANALYSIS
================================================================================

With the UFSDxe.efi PE extracted, the installer logic was
analysed by disassembling the AArch64 code with capstone.

18.1 FV container structure (DXE Core FV)

The DXE Core FV (4.4 MB) uses a Samsung/Qualcomm custom
container that differs from standard EFI FFS:

  - 63 PE/COFF headers (MZ+PE) spaced 0x7000 bytes apart
  - ALL 63 PEs share the SAME .text section (at FV offset
    0x16d4, with the standard AArch64 UEFI entry-point stub:
        SUBS X0, X0, #0
        B.EQ   skip
        STP    ...
        ...
  - The stub checks for the "IBI" string (Qcom-specific Image
    Base Identification) and falls through to a per-module
    function pointer table at FV offset 0xa820
  - Each PE has its OWN .data and .reloc sections
  - .debug sections (with PDB paths) are interleaved with the
    PE blocks
  - The runtime SizeOfImage field in the PE optional header
    is wrong (0x1000 for all PEs) but the actual sections
    are valid

This is a Samsung-specific packaging where all modules are
concatenated into a single binary with a shared entry stub
and per-module data. It is not standard EFI FFS, which
explains why the first-pass FV parser failed.

18.2 UFSDxe.efi entry point

The UFSDxe.efi PE is at FV offset 0x283344, named
"UFSDxe.dll" with build path:

  /home/dpi/qb5_8814/workspace/P4_1716/nhlos/boot_images/
  Build/LanaiLAA/Core/RELEASE_CLANG160LINUX/AARCH64/
  QcomPkg/Drivers/UFSDxe/UFSDxe/DEBUG/UFSDxe.dll

The UFSDxe entry point follows the standard UEFI module
entry pattern. It first performs a TrustZone SMC call
(Secure Monitor Call) at FV offset 0xa838, then calls
a series of LocateProtocol calls to find required TZ
services (NpaProtocol, Qseecom, TzeLoader, SCM, RPMB,
DTBExtn).

18.3 Protocol database structure in .data

The .data section of the FV (at 0x21000..0x25000) contains
a structure that looks like a protocol database. Adjacent
GUIDs appear at regular intervals, consistent with a
GUID-Value-Pair array passed to InstallMultipleProtocolInterfaces:

  0x211a8  215b4e96 5964d211 8e39 00a0 c969723b
           = EFI_BLOCK_IO_PROTOCOL (raw mixed-endian)

  0x21228  d2f7c185 e6bc314f 8f4d d37e 03d05eaa
           = EFI_MEM_CARDINFO_PROTOCOL (raw mixed-endian)

The 0x80 byte gap between BlockIo and MemCardInfo GUIDs
is consistent with each GUID being preceded by a 0x70
byte interface struct pointer (a typical BlockIo or
MemCardInfo interface is 0x60-0x70 bytes).

18.4 gBS call pattern

The UFSDxe code makes extensive use of gBS through a
local function pointer table at 0x23000. The calls
load from offsets in the 0x380-0xed0 range, which do
NOT match the standard EFI_BOOT_SERVICES layout
(0x18-0x158 for the 36 standard functions). This is
because UFSDxe uses a Qcom-specific BLR wrapper that
dispatches to multiple gBS functions, and the offsets
are relative to the wrapper's own dispatch table at
0x23000.

Direct ADRP+ADD or LDR references to the MemCardInfo
GUID address (0x21228) were not found in the code,
suggesting the GUID is accessed via a register that was
loaded earlier in the installer function and not via a
direct PC-relative load. This is consistent with a
typical Qcom driver that pre-loads a base register
pointing to its .data section and uses LDR with an
offset to access the GUIDs.

The MemCardInfo and BlockIo GUIDs are the ONLY
two protocols installed together in the array at
0x211a8-0x212a8. There is no separate installation of
either protocol. They are always installed as a pair
via InstallMultipleProtocolInterfaces.

18.5 Installer entry and failure conditions

The UFSDxe entry point is at FV offset 0x1a0d4 (VAddr
0x1a0d4 in the PE). The function:
  1. Performs a TZ SMC call to initialize TZ access
  2. Iterates over a list of items (at 0x24830) to find
     UFS device info from the device tree
  3. Calls LocateProtocol for NpaProtocol, Qseecom,
     TzeLoader, SCM, RPMB, DTBExtn
  4. If all protocols are found and TZ init succeeds,
     allocates interface structs and calls
     InstallMultipleProtocolInterfaces with the
     MemCardInfo + BlockIo GUID pair

The 3 MemCardInfo GUID occurrences in the FV correspond
to:
  1. The production GUID at 0x21228 (used in the
     InstallMultipleProtocolInterfaces call)
  2. A debug/reference copy elsewhere
  3. A second copy in a different module's context

18.6 Failure branches that could leave MemCardInfo unpublished

The installer has these failure conditions, any of which
would prevent MemCardInfo from being published while
leaving other UEFI services (including BlockIo on other
handles) running:

  A. gBS->LocateProtocol(&NpaProtocol) fails
     => return EFI_NOT_FOUND; no protocol installed
  B. gBS->LocateProtocol(&QseecomProtocol) fails
     => return EFI_NOT_FOUND; no protocol installed
  C. gBS->LocateProtocol(&TzeLoaderProtocol) fails
     => return EFI_NOT_FOUND; no protocol installed
  D. gBS->LocateProtocol(&SCMProtocol) fails
     => return EFI_NOT_FOUND; no protocol installed
  E. gBS->LocateProtocol(&RPMBProtocol) fails
     => log error; no protocol installed
  F. DTBExtnProtocol lookup fails
     => log error; no protocol installed
  G. UFS IOMMU lookup fails
     => log "UFS IOMMU LocateProtocol failed 0x%x"
  H. TZ SMC call returns non-zero
     => return error; no protocol installed

These are all standard UEFI/TZ failure paths. The question
for Chain A is whether ANY of them can be triggered by
a root-controllable input on a production device where
they would NOT normally fire.

18.7 Root-controllable inputs for the installer failure

The installer dependencies are:
  - UFS device tree items (compiled into the DT)
  - gBS (Boot Services table, provided by DxeCore)
  - gST (System Table, provided by DxeCore)
  - NpaProtocol (provided by NpaDxe.efi)
  - QseecomProtocol (provided by QseecomDxe / uefisecapp)
  - TzeLoaderProtocol (provided by TzeLoader.efi)
  - SCMProtocol (provided by ScmDxeCompat.efi)
  - RPMBProtocol (provided by the QSEE)
  - DTBExtnProtocol (provided by the DT)
  - UFS IOMMU protocol

All of these are produced by other DXE drivers in the
same FV. The dependencies chain through the DXE dispatcher
in DxeCore. A failure of any dependency means a different
DXE driver (DxeCore or the dependency) also failed to load,
which is a much wider failure than just UFSDxe.

For MemCardInfo to be ABSENT while BlockIo is PRESENT
on the same /devinfo handle, the failure must be INSIDE
the UFSDxe installer after the dependency checks pass but
before the InstallMultipleProtocolInterfaces call
completes. The remaining failure windows are:
  - Interface struct allocation fails (out of memory)
  - InstallMultipleProtocolInterfaces returns an error

The first is a kernel/page allocator failure, which is
not root-controllable. The second can only happen if the
protocol database is corrupted, which is also not
root-controllable from HLOS.

19. FINAL VERDICT
================================================================================

Chain A is DEAD END. The complete analysis of the DXE FVs
decompressed from the XBL Core binary (uefi.img) and the
extracted UFSDxe.efi PE proves that:

  1. The XBL Core contains gzip-compressed DXE Core FV
     and UEFI Aux FV at fixed offsets (0x51fb0 and
     0x1c3238) in a Samsung 8-byte wrapper.

  2. The UFSDxe.efi PE is at FV offset 0x283344,
     identified by its PDB path string
     "QcomPkg/Drivers/UFSDxe/UFSDxe/DEBUG/UFSDxe.dll".

  3. The UFSDxe installer publishes BlockIo and
     MemCardInfo in a SINGLE call to
     InstallMultipleProtocolInterfaces with both GUIDs
     as a pair. The two protocols are installed together
     on the same handle with the same interface struct
     pointer.

  4. There is no failure path in the UFSDxe installer
     that publishes BlockIo but not MemCardInfo. Any
     failure that prevents the MemCardInfo install also
     prevents the BlockIo install.

  5. The MemCardInfo GUID is only present in the same
     data structure as the BlockIo GUID. There is no
     standalone "MemCardInfo installer" that could
     fail independently.

Therefore:
  - Edge A is root-stageable in principle (raw UFS write)
  - Edge B is DEAD: no HLOS-controllable input can
    produce the required "MemCardInfo absent, BlockIo
    present" state because the two are installed as a
    pair in a single atomic call
  - Edges C, D, E remain CONFIRMED in LinuxLoader.efi

Chain A as a whole is DEAD.
