1. EXECUTIVE CONCLUSION
================================================================

Q1. Can temporary Android root prepare a DeviceInfo that ABL accepts with IsUnlocked=1?
    YES. Persistence is raw UFS, the only integrity gate is a 13-byte magic comparison,
    and there is no other signature, CRC, hash, MAC, RPMB channel, or secure-world check.

Q2. What integrity values, if any, must be recomputed?
    None. The structure is plain fields behind a 13-byte literal magic.

Q3. Does any EM initialization failure preserve an existing +0x0d=1 without
    requiring the MemCardInfo error path?
    NO. The audited flow always reaches SetUnlock with the current GetEMBit(3) result.
    The Engineering Mode bitmap at 0x18c9e0 is zero in the .data section, so any
    BLInitToken / GetEMBit failure collapses to SetUnlock(0), which writes +0x0d=0 and
    persists it. The only static EM-bypass is the MemCardInfo LocateProtocol error
    path (0x93f0 tbnz, 0x9420).

Q4. Is there evidence that MemCardInfo can disappear while ordinary UFS/BlockIo
    remains usable?
    UNKNOWN / EXTERNAL. The MemCardInfo installer lives in the ABL inner FV
    (abl-inner-oneui8.fv.bin). Its DXE driver symbols are not in the audited
    artifacts, so its failure modes cannot be enumerated statically. The standard
    BlockIo GUID is not visible in the audited LinuxLoader or inner FV, so the
    independence of "BlockIo alive" vs "MemCardInfo gone" is not provable here.

2. DEVICEINFO PERSISTENT FORMAT
================================================================

Live structure
   base  0x170e28, size 0xcd0, FirstReadDevInfo@0x170e20
   IsUnlocked  +0x0d
   +0x0e       next 2 bytes (status / counter region)
   +0x90       u8 1 (present on this device)
   +0xc88      u32 UnlockCount (zero on this device)

Persisted on
   /dev/block/by-name/devinfo -> /dev/block/sda15
   size 4096 bytes (4 KiB), UFS user partition
   not mounted as a filesystem (raw block device)

Read path
   Function 0xff30 (VB protocol wrapper):
     LocateProtocol wrapper at 0x10aac loads gBS->LocateProtocol (offset 0x140),
     adds 0xf80 to the caller's page. The caller passes page 0xe2000, so the GUID
     resolved is at 0xe2f80 = 8e5eff91-21b6-47d3-af2b-c15a01e020ec.
     CORRECTED (section 15): that GUID is not a Samsung BlockIo-like interface.
     It is Qualcomm's Verified Boot protocol, gEfiQcomVerifiedBootProtocolGuid.
     The producer is Qualcomm's own VerifiedBootDxe, module
     decompiled/dxe_modules/DXE_FV_MAIN_fd975fb5-92c3-40b3-b05c-9c434326ab64.efi
     in the DXE FV of the uefi partition, GUID literal at module offset 0xd0b8.
   Argument shape: 0xff30(w0=op, x1=buf, w2=bytes).
     CORRECTED (section 15): w0 is the operation code, not a partition slot.
     w0=0 is the read op and w0=1 is the write op. The upstream public PoC
     (kasnria001/qualcomm_gbl_exploit_poc, VbRwStateApp.c) calls the same
     protocol as VBRwDeviceState(op, buf, len) with READ_CONFIG=0 and
     WRITE_CONFIG=1. Our two call sites carry exactly those values.
     RESOLVED (section 16): the binding is exact across both binaries.
     0xff30 does `ldr x8, [x0, #8]` then `blr x8`, with x0 = the interface,
     x1 = op, x2 = buffer, x3 = length, and the member at protocol offset
     +8 in the driver's own table is RWDeviceState at 0x15a4.
   DeviceInfoInit (0x425ec) calls 0xff30(0, &live, 0xcd0) once on first entry
   (guarded by FirstReadDevInfo@0x170e20 bit 0).

Write path
   Function 0xff30 (write op) for 0xcd0-byte whole-structure writes.
   Helper 0x42edc is an inline (x0=1, x1=&live, x2=0xcd0) write-op wrapper.
   Persist callsites in the audited PE (RVA, mode, buffer, +0x0d effect):
     0x095d4  read  scratch 0x15af10         copies persistent byte to scratch
     0x09914  write same scratch              writes preserved scratch byte
     0x423e0  write live DevInfo              persists current byte
     0x42468  read  live DevInfo              overwrite byte from persistence
     0x42528  write live after SetUnlocked    persists explicit new byte
     0x425a4  write live after +0x0e update   persists unchanged +0x0d
     0x4261c  read  live DevInfo              first-load overwrite from persistence
     0x42708  write live defaults             persists explicit zero
     0x428b0  write live key-record update    persists unchanged +0x0d
     0x42dc8  write live tail-field update    persists unchanged +0x0d
     0x42f10  write live key-record helper    persists unchanged +0x0d
     0x58df4  read  allocated scratch         copies persistent byte to scratch
     0x58f54  write same scratch              writes preserved scratch byte

   Only SetUnlocked (0x424cc) explicitly writes a new value into live +0x0d
   (and persists it). All other writes copy whatever is currently in the live
   structure, so they do not by themselves destroy a +0x0d=1 that was already
   loaded.

3. DEVICEINFO LOAD VALIDATION (the entire integrity gate)
================================================================

The whole validation is in 0x425ec..0x42710 and reduces to:

   0x425ec DeviceInfoInit
     0x42608 tbnz [0x170e20], #0, 0x42654         ; skip read if FirstReadDevInfo
     0x4261c bl  0xff30                            ; ReadBlocks -> live
     0x42654 adrp x19, 0x170000; add x19, #0xe28    ; x19 = &live
     0x4265c bl  0x42f34 (tail-call: x0=x19, x1=&"SAMANDR-BOOT!", x2=13)
     0x42660 bl  0xf2ec                            ; memcmp(live, magic, 13)
     0x42664 cbz  x0, 0x4273c                      ; magic OK -> return NULL
     0x42668 .. 0x42688                            ; debug log on mismatch
     0x4268c default-init:
        memset 0x170e28..0x171af8 (0xcd0)
        strb wzr, [x19, #0xd]                      ; live +0x0d = 0
        strb w8,  [x19, #0x90]                     ; live +0x90 = 1
        bl  0xff30                                  ; WriteBlocks (persists zeros)
     0x4273c mov x19, xzr
     0x42748 mov x0, x19; ret

   Validation performed on the loaded structure:
     magic (13 bytes)               YES
     version                        NO
     size                           NO
     CRC / checksum                 NO
     hash                           NO
     HMAC / MAC / digital signature NO
     encrypted / authenticated container NO
     replay / rollback / monotonic counter NO
     RPMB-backed metadata           NO
     secure-world state             NO
     duplicated / redundant copies  NO
     partition GUID / type          NO
     anything derived from secure hardware  NO

   The thunk at 0x42f34 is a tail-call that sets x0/live, x1/magic, x2/13 and
   returns into 0x42660 (bl 0xf2ec). 0xf2ec in turn tail-calls the memcmp
   implementation at 0xf440 after pointer/range checks. The only integrity
   decision is the return value of memcmp.

   What happens on failure:
     - The full 0xcd0-byte live structure is zeroed, including +0x0d.
     - +0x90 is set to 1, +0xc88 is zeroed.
     - The cleared 0xcd0 bytes are written back to the partition.
     - Return value is non-zero (the function returns the WriteBlocks result
       which is the live buffer address or a wrapper), so the caller's
       cbz 0x9464 is NOT taken and the boot diverges into the fatal/debug
       branch at 0x93fc. The function does NOT abort the boot by itself.

   An externally modified but structurally valid DeviceInfo
     magic valid
     IsUnlocked = 1
     all other fields unchanged
   would be accepted by the loader. The only check on the next boot is the
   13-byte memcmp, and +0x0d is not touched by DeviceInfoInit itself when
   the magic is valid.

Block-device path:

5. CAN ROOT MANUFACTURE AN ACCEPTED IsUnlocked=1 DEVICEINFO?
================================================================

YES, in principle.

Required manipulations, all reproducible on the device with root:
   1. Read /dev/block/sda15 into a 4 KiB buffer.
   2. Verify or set bytes [0..12] to "SAMANDR-BOOT!" (13 bytes).
   3. Set byte 0x0d to 1.
   4. Optionally zero bytes outside the fields AVB/AVB-ops care about.
   5. Write the 4 KiB back to /dev/block/sda15.

No CRC, signature, HMAC, version, RPMB counter, or any other integrity
value has to be recomputed. The audited validation is memcmp(magic, 13).

The only obstacle is not integrity: it is EM sync overwriting +0x0d in
the next boot. That obstacle is analyzed in section 6.

6. EM SYNC FAILURE MATRIX
================================================================

The audited EM sync sequence is fixed and linear:

   0x9984 bl 0x44d40  -> w21 = BootLockState (1=locked, 0=unlocked)
   0x998c bl 0xade70  -> BLInitToken (TA open + send cmd 0x19, then 0x15)
   0x9990 mov w0, #3
   0x9994 bl 0xadae0  -> GetEMBit(3) (lsr+and on qword 0x18c9e0[3])
   0x999c mov w1, 0
   0x999a0 cset w0, ne   (1 if bit set, 0 if clear)
   0x999a4 bl 0x41f88  -> SetUnlock dispatcher(w0=bit, w1=0)
   0x999a8 mov w0, w21
   0x999ac bl 0x4e360  -> UI flow / next boot step

The global bitmap at 0x18c9e0 is all-zero in .data at file offset 0x18c9e0
(initial value 32 bytes of 0x00). Any BLInitToken that does not populate
this array leaves GetEMBit(3) returning 0, which collapses to SetUnlock(0).

| Stage                 | Failure source        | On failure                              | SetUnlock called? | Value passed | AVB reachable? | Existing +0x0d survives? |
|-----------------------|-----------------------|-----------------------------------------|-------------------|--------------|----------------|--------------------------|
| BootLockState 0x44d40 | locked                | continues into EM sync                  | YES               | bit value    | YES (after sync) | depends on bit            |
| BLInitToken 0xade70   | TA open / cmd 0x19    | returns 0 without populating bitmap      | YES               | GetEMBit(3)  | YES             | NO if bit is 0 (zeros)   |
| BLInitToken 0xade70   | cmd 0x15 alt path     | same                                    | YES               | GetEMBit(3)  | YES             | NO if bit is 0            |
| BLInitToken 0xade70   | TA unavailable        | return non-zero, no bitmap update       | YES               | GetEMBit(3)  | YES             | NO if bit is 0            |
| GetEMBit 0xadae0      | bitmap empty          | returns 0                                | YES               | 0            | YES             | NO (zeros, persisted)     |
| GetEMBit 0xadae0      | bitmap populated      | returns bit value                        | YES               | bit value    | YES             | YES if bit=1, NO if bit=0|
| SetUnlock dispatcher  | dispatcher internal   | early-return paths skip live write      | NO (no 0x0d write) | n/a          | YES             | YES (existing survives)   |
| LocateProtocol MemCardInfo | success          | normal path                              | YES               | bit value    | YES             | NO if bit=0               |
| LocateProtocol MemCardInfo | error (0x93f0)    | jumps to 0x9420 -> lazy DeviceInfoInit  | NO                | n/a          | YES (direct)    | YES (no overwrite at all) |

Conclusions for EM sync failure:
   CASE 1 (failure -> SetUnlock(0) -> persisted 1 destroyed):
       the standard outcome for any TA / bitmap failure.
   CASE 2 (failure -> SetUnlock skipped, existing survives):
       possible only via the MemCardInfo LocateProtocol error path.
   CASE 3 (failure -> boot aborts before AVB):
       no such path was found in the audited LinuxLoader.
   CASE 4 (failure -> uninitialized/stale value reaches SetUnlock):
       the bitmap is all-zero in .data; "stale" in the static sense means zero,
       so the result is CASE 1, not CASE 2.

   The MemCardInfo LocateProtocol error path is the only static state-preservation
   edge. The BootLockState pre-check (locked) does NOT skip EM sync; the EM
   sequence still runs and a locked device ends with a SetUnlock(0) write
   (assuming bit 3 is clear in the locked case, which is the normal state).

7. EASIER STATE-PRESERVATION PATHS RANKED
================================================================

Ranked from "easiest" to "hardest" by how much of the precondition is
within reach of the static audit:

1. MemCardInfo LocateProtocol error (0x93f0 tbnz -> 0x9420)
   - The only static state-preservation path that skips EM sync entirely.
   - Triggered only by an EFI error returned by the UFS/SDCC MemCardInfo
     installer. The installer lives in the ABL inner FV and is not
     enumerable from the audited LinuxLoader artifacts.
   - Reachable for the lazy DeviceInfoInit at 0x98fbc; the live +0x0d byte
     is loaded from the persisted structure and is not overwritten on the
     way to AVB.
   - Verdict: POSSIBLE in structure, EXTERNAL precondition.

2. Bit 3 of 0x18c9e0 already set to 1 at boot
   - Would make GetEMBit(3) return 1, which leads to SetUnlock(1), which
     would write +0x0d=1 and persist it.
   - But the static initial value of 0x18c9e0 is zero, and there is no
     audited writer of 0x18c9e0 other than BLInitToken. So this requires
     BLInitToken to succeed AND to have populated bit 3.
   - This is the OEM Engineering Mode "kernel cust" path, not an attacker-
     controllable state in the audited scope.

3. BootLockState=1 with EM bit 3 set
   - 0x9984 returns 1, but the EM sequence still runs and writes the
     bitmap's bit 3. A "locked + kernel cust" device is not static-attacker
     reachable.

4. SetUnlock dispatcher internal error paths
   - The dispatcher can early-return without writing live +0x0d (e.g.
     when the read-only flag is set or when the value is unchanged), but
     this still leaves the live +0x0d alone; it does not get the byte to
     AVB unless a different path populated it. Not useful as a state
     preservation channel by itself.

There is no other path. Rank 1 is the only plausible Chain A anchor.

10. DEAD ENDS
================================================================

These paths were considered and rejected for state preservation:

   - BootLockState pre-check returning 1: still runs the EM sequence; ends
     in either SetUnlock(0) (if bit 3 clear) or SetUnlock(1) (if bit 3 set).
     Not a generic +0x0d preservation path.
   - FirstReadDevInfo guard: this is a one-shot guard inside DeviceInfoInit,
     not an alternative to EM sync. It cannot preserve +0x0d on its own.
   - SetUnlock dispatcher early-return (no live write): preserves the
     existing live +0x0d but does not introduce a non-zero +0x0d either.
   - Alternate cmd 0x15 path of BLInitToken: same end state, populates
     the bitmap; failure collapses to GetEMBit(3)=0 -> SetUnlock(0).
   - Any of the 12 whole-structure writes (0x42528, 0x425a4, 0x42708,
     0x428b0, 0x42dc8, 0x42f10, 0x58f54, 0x95d4, 0x9914, etc.) with
     EM sync still in flight: they all persist whatever +0x0d already is,
     and EM sync still runs SetUnlock(0/1) afterwards.
   - The "string absences" in evidence: '[OEM]Oem unlock value is %d' and
     '[FRP][OEM] init succeed!' are absent in the audited PE. No other
     'Oem unlock' writer was found in the LinuxLoader. SetUnlocked remains
     the only +0x0d writer in the audited PE.

15.1 FINDING 1: the protocol identity

   GUID 8e5eff91-21b6-47d3-af2b-c15a01e020ec is Qualcomm's Verified Boot
   protocol. The producer is Qualcomm's own driver, VerifiedBootDxe, in the
   DXE FV of the uefi partition. GUID literal at module offset 0xd0b8.

   Its own strings name the operation we have been calling "ReadBlocks" and
   "WriteBlocks":

     VB: RWDeviceState: Succeed using devinfo!
     VB: RWDeviceState: Succeed using rpmb!
     VB: RWDeviceState: read_partition err! status: %d
     VB: RWDeviceState: write_partition err! status: %d
     VB: RWDeviceState: invalid operation op = %x
     VB: RWDeviceState: Invalid parameters!
     VB: RWDeviceState: mem allocation for write failed!
     VB: RWDeviceState: Cannot read security state!
     VB: RWDeviceState: Cannot read security state with no rpmb check!
     VB: RWDeviceState: Cannot locate gQcomQseecomProtocolGuid!
     VB: DeviceInit: Device is unlocked! Skipping verification!
     VB: readSecurityState: Locate SCM Status: (0x%x)

   "invalid operation op = %x" is the direct refutation of the
   "partition_slot" reading. The first argument is an operation code.

   The protocol struct is the 0x68-byte table at .data 0xd180 of the module:
   +0x00 is the scalar header word 0x0000000000010003, not a function
   pointer, and the member the PoC calls VBRwDeviceState sits at +0x08. The
   PoC's "first member at offset 0" is a property of the PoC's header, not
   of this driver. The ABL helper 0xff30 loads the interface member at +8
   and calls it, so the two binaries agree on the same slot.

   CONFIRMED. Full body in decompiled/vb-protocol-8e5eff91-evidence.txt.

15.2 FINDING 2: our call sites are VBRwDeviceState, and the op values match

   Our two call shapes:

     read   0xff30(0, &live, 0xcd0)
     write  0x42edc -> (x0=1, x1=&live, x2=0xcd0)

   The PoC's API:

     VBRwDeviceState(proto, op, buf, len)   READ_CONFIG = 0, WRITE_CONFIG = 1

   Same argument positions, same op values, same buffer, same length. Our
   ABL has been calling VBRwDeviceState since the start. The "custom
   BlockIo-like interface" model was a mis-parse of the op argument.

   CONFIRMED.

15.3 FINDING 3: the +0x0d offset is independently confirmed

   The PoC's relock application writes Buf[13] and Buf[14]. Our devinfo
   IsUnlocked is at +0x0d = 13, and +0x0e is the next field in the status
   region. Two independent implementations agree on the offset.

   CONFIRMED for the offset. The PoC's buffer is 3344 bytes (0xd10) against
   our 0xcd0 devinfo. RESOLVED (section 16): the driver has no fixed
   structure size. The devinfo path is a whole-partition read-modify-write
   that overlays min(BufferSize, partitionSize) bytes at offset 0 of the
   partition, and the only size checks are Buffer != NULL, BufferSize != 0
   and BufferSize <= partitionSize on write. The two sizes are not a
   conflict, the PoC's buffer is simply longer than the partition it
   writes and the extra bytes are discarded.

   One caveat the PoC and this driver cannot settle between them: the
   semantics of offset 0x0d. The Qualcomm driver never reads any field of
   the buffer, so it has no notion of a lock byte. +0x0d is a Samsung ABL
   convention. The two agree on the offset, neither can confirm what it
   means.

15.5 CONSEQUENCE FOR CHAIN A, EDGE B

   Edge B needed the state "MemCardInfo absent, VB present, devinfo
   readable". It was previously argued that this state is unreachable
   because VB is published by the same driver that publishes MemCardInfo,
   and that driver installs both as a pair.

   The first half of that argument is now refuted. VB and MemCardInfo come
   from different drivers, so UFSDxe failing to install does not by itself
   remove the VB protocol. The second half, that UFSDxe installs BlockIo
   and MemCardInfo as a pair, is untouched and still holds.

   The argument does not collapse, it reduces to one question:

     Does VerifiedBootDxe's devinfo read and write path depend on the
     BlockIo instance that UFSDxe installs?

     If yes: VB present implies UFSDxe ran implies MemCardInfo present,
     Edge B stays unreachable, and Chain A stays dead, but now for a
     stated and checkable reason rather than an inferred one.

     If no: VerifiedBootDxe reaches the partition by its own path, then
     UFSDxe's installer failing (its dependency list is enumerated in
     decompiled/uefi-memcardinfo-producer-analysis.txt section 18.6) leaves
     the VB protocol alive and devinfo readable while MemCardInfo is
     absent. That is exactly the Edge B precondition, and Edge B becomes
     reachable.

   The "Succeed using rpmb!" branch matters here. The driver has a second
   storage path that goes through Qseecom and the RPMB namespace rather
   than through UFS, and the PoC README states the lock state lives in
   RPMB on the devices it targets. Which branch this device takes, and
   what each branch depends on, is what the RWDeviceState body answers.

   Status at time of this edit: OPEN, single question, answerable from
   decompiled/dxe_modules/DXE_FV_MAIN_fd975fb5. The VerifiedBootDxe
   RWDeviceState body was being disassembled for exactly this. Until that
   lands, the correct label for Edge B is OPEN, not DEAD.

   This section does not assert that Edge B is reachable. It asserts that
   the previous DEAD verdict rested on a premise that has been refuted,
   and names the replacement question.

   ANSWERED (section 16): the answer is "yes, it depends". VerifiedBootDxe
   has no block access of its own. Edge B stays unreachable and Chain A
   stays dead, on a stated and mechanically derived reason. Section 16
   replaces the OPEN label with the final one.

16.1 THE ANSWER TO SECTION 15.5

   NO. The devinfo path is not independent of the storage driver.

   VerifiedBootDxe has no block access of its own. The RWDeviceState body
   at actual 0x15a4 resolves the partition by LABEL and then goes through
   the block interface of the handle it finds.

16.2 THE MECHANISM

   The devinfo branch of RWDeviceState (write at actual 0x1930, read at
   0x1954) calls the module's own write_partition / read_partition helpers
   with the CHAR16 label "devinfo" (ASCII literal at 0x8d40, converted by
   the module's convert_char8_to_char16 at 0x2880). "devinfo" is the only
   occurrence of that string in the whole 109-module corpus, it is a GPT
   partition label known to this driver only.

   read_partition (0x28d4) and write_partition (0x2a74):

     - enumerate handles exposing EFI_BLOCK_IO_PROTOCOL,
       964e5b21-6459-11d2-8e39-00a0c969723b, with LocateHandleBuffer at
       gBS+0x138, helper actual 0x4614, then HandleProtocol per handle
       for the device path, GUID 09576e91-..., at actual 0x4758, and match
       the label against the partition's device path.
     - read: ReadBlocks at +0x18 into a pool buffer sized to the whole
       partition, then CopyMem(Buffer, BufferSize, scratch, partitionSize).
     - write: partitionSize computed at 0x2b48 as
       `madd x24, x8, x9, x8` over the media descriptor, x8 = u32 at
       media+0x0c (BlockSize) and x9 = u64 at media+0x18 (Offset), giving
       BlockSize * (Offset + 1), the partition size in bytes. If
       BufferSize > partitionSize the call is rejected with
       "write_partition: buffer is too big!". Otherwise the whole partition
       is read into scratch, the user's bytes are overlaid at offset 0, and
       the whole partition is written back.
     - the block interface carried by the handle has Media at +0x08,
       ReadBlocks at +0x18 and WriteBlocks at +0x20, which is the published
       EFI_BLOCK_IO_PROTOCOL layout, and the calls use the classic
       (This, MediaId, LBA=0, Size, Buffer) shape.

   The block interface and the partition enumeration are published by the
   storage driver, not by VerifiedBootDxe. VerifiedBootDxe only consumes
   EFI_BLOCK_IO_PROTOCOL; it does not install it. It installs exactly one
   protocol, the VB one, and the only other GUID it carries is
   EFI_SIMPLE_FILE_SYSTEM at 0xd138.

   So: no storage driver, no BlockIo, no devinfo handle, and the driver's
   own error strings spell out the failure:
     "read_partition: Failed to get handle (label = %s)"
     "read_partition: Image partition not found"
     "read_partition: readblocks was unsuccessful"
     "write_partition: Image partition not found"
     "write_partition: writeblocks was unsuccessful"

16.3 THE ABL SIDE

   When the VB read fails, the ABL does not fall back to anything. In
   DeviceInfoInit:

     0x04261c  bl  #0xff30            ; VBRwDeviceState(READ_CONFIG, &live, 0xcd0)
     0x042620  cbz x0, #0x4264c        ; status == 0 -> success, go to magic check
     0x042624  mov x19, x0             ; error: keep the status
     0x042628  bl  #0x1c70
     0x042630  b.eq #0x42740
     0x042634  bl  #0x42e3c
     0x042640  adrp x1, #0xc9000
     0x042648  b   #0x42734            ; log and leave
     ...
     0x04273c  mov x19, xzr            ; magic OK -> return NULL
     0x042740  bl  #0x42e10
     0x042744  b.ne #0x42758
     0x042758  bl  #0x14a4             ; error exit

   The live DevInfo is never populated, the persisted +0x0d never reaches
   AVB, and the default-init path at 0x4268c is not taken either, because
   that is the magic-mismatch branch, not the read-failure branch.

   The 0x42620 check is the exact point where a failed VB read diverges.
   Before this pass it was read as an argument-shape artefact.

16.4 WHICH BACKEND RUNS ON THIS DEVICE

   RWDeviceState has two backends. RPMB is taken only when the SCM
   security state word has none of the bits in 0x8703 AND the SecurityFlag
   byte has bit 7 set. Otherwise it is the devinfo path, which is the
   fallback.

   The devinfo path is the one in use on this device, and the artifact
   proves it. partitions/devinfo.img carries the 13-byte magic
   "SAMANDR-BOOT!", +0x0d = 0 and +0x90 = 1, with everything else zero.
   That is exactly the shape of the ABL's default-init write at 0x4268c:
   memset 0xcd0, +0x0d = 0, +0x90 = 1, WriteBlocks. The only writer of
   that partition is the ABL through the VB protocol. If the RPMB branch
   were the one running, that write would have gone to the RPMB blob and
   devinfo.img would be blank. It is not blank. CONFIRMED.

16.5 FINAL CHAIN A VERDICT

   Edge A (root -> persisted devinfo +0x0d=1):
     ROOT-STAGEABLE in principle. Unchanged. The 13-byte magic is still
     the only integrity gate on the persisted structure and
     /dev/block/sda15 is HLOS-writable.

   Edge B (persisted +0x0d=1 reaches AVB without EM sync):
     UNREACHABLE. The only static state-preservation path is the
     MemCardInfo LocateProtocol error, and MemCardInfo is installed by
     UFSDxe in the same InstallMultipleProtocolInterfaces call as
     EFI_BLOCK_IO_PROTOCOL. VerifiedBootDxe's devinfo path consumes
     EFI_BLOCK_IO_PROTOCOL and has no access of its own, so when the
     storage driver is gone the devinfo read fails, DeviceInfoInit
     diverges at 0x42620 and the persisted byte never reaches AVB.
     CONFIRMED, mechanically derived, not inferred.

   Edge C (AVB read_is_device_unlocked returns 1): CONFIRMED.
   Edge D (AVB skips verification): CONFIRMED.
   Edge E (BootLinux / kernel handoff): CONFIRMED.

   Chain A overall: DEAD END. The outcome matches the original section 19
   verdict, but the mechanism is now stated correctly: not "UFSDxe installs
   MemCardInfo and BlockIo as a pair" alone, but "the VB protocol that
   carries the lock byte rides on the same storage driver, through the
   same BlockIo".

   The intermediate reopening in section 15.5 of this file and in
   decompiled/uefi-memcardinfo-producer-analysis.txt section 20 was based
   on the refuted premise that the VB protocol has a lifetime independent
   of the storage driver. It does not. The reopening is closed, and it
   closed against the reopening, not for the original reasoning.

16.6 WHAT THE PoC CONTRIBUTED, NET

   It identified the protocol our ABL uses for devinfo, it confirmed the
   +0x0d offset against an independent implementation, and it produced the
   upstream reference for the interface shape. It did not and could not
   produce a GBL route for this device; the GBL component is absent from
   every Samsung bootloader in the corpus, there is no efisp partition and
   there is no Android fastboot protocol.
