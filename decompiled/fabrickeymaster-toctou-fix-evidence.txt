FABRICKEYMASTER CVE-2026-21046 PATCH-DIFF: TRUE DELTA IS 0x23ac + VALIDATOR LIMIT
Follow-up to notes/keymaster-initial-findings.md. Both fabrickeymaster SPU builds
are in hand, so the diff runs entirely offline against local files.

CORRECTION (2026-09): the first version of this file claimed the fix was six
identically-patched dispatch stubs (unconditional stamp -> re-read + cmp + br).
That claim is REFUTED. Same-VA comparison across a shifted binary compared a
stamp function against a check function: both builds contain the same 8 stamp
stubs AND the same 6 check stubs (identical slots, identical cmp immediates,
e.g. BEFORE check-8 @0x1ae38 vs NEW check-8 @0x1aec8 differ only in branch/log
targets). The stamp/check split predates the patch. The (slot, tag) "rotation"
noted earlier was the same artifact. What follows is the content-matched
re-analysis; the raw VA-aligned dumps are kept because they are reproducible,
not because their interpretation below still stands.

METHOD
  1. scripts/ta_patchdiff.py (unmodified) on the two ELFs
     -> decompiled/fabrickeymaster-dzdp-vs-dzg1-patchdiff.txt
     Naive VA-aligned: before=2691 after=2691 functions, ADDED=2582
     REMOVED=2582 COMMON=109, byte-changed=98. Code segment grew 0x100 with the
     first divergence at VA 0x21a, so VA alignment is garbage downstream: the
     2582/2582 and the 98 are ~entirely shift noise, not 98 changed functions.
  2. scripts/fkm_classify_changes.py over the 98
     -> decompiled/fabrickeymaster-mnemonic-classify.txt (42 noise / 56 real).
     Same caveat, stronger: mnemonic comparison of VA-misaligned PAIRS still
     compares different functions (stamp body vs check body). The 56 are
     candidates of a broken pairing, not 56 changed functions. Kept as raw
     tool output; superseded by step 4.
  3. scripts/fkm_trace_callgraph.py --image <before> --targets <bti entries>.
     Entry VAs are the bti c landing pads (stp VA - 8). Caller lists below
     reproduce exactly against the BEFORE image.
  4. Content matching (no committed script; procedure: TPD.detect_functions on
     both ELFs, index NEW by exact mnemonic sequence, match BEFORE against it).
     Result: 2688/2691 BEFORE functions have an EXACT mnemonic-sequence match
     in NEW. Only 3 lack one: 0x1d2c (same-VA match at 0.981: one constant),
     0x23ac (same VA, heavily reworked), 0x1b748 (matches NEW 0x1b7d0 at
     0.987; the only delta is two absorbed udf#0 padding words: NOT a change).
     True delta: TWO functions.

TRUE DELTA 1: validator limit 0x4b000 -> 0x4b080 (inside 0x1d24)
  0x1d24 is the bounds validator: ldr w8,[x0,#4]; w19 = w8+8; reject unless
  w19 <= limit. BEFORE hardcodes the limit (cmp w19,#0x4b,lsl#12 = 0x4b000);
  NEW loads it (mov w20,#0xb080; movk w20,#4,lsl#16; cmp w19,w20). Same +0x80
  (128) growth as the id range below; consistent with new key/algorithm slots,
  not logic.

TRUE DELTA 2: dispatcher 0x23ac reworked (311 -> 345 ins, +34 net)
  Big dispatcher (300+ ins, log-heavy, no direct bl callers: reached
  indirectly). w24 is the validated count/index feeding the jump-table
  dispatch at the tail (table base 0x105880 + w24*16, entry+8 loaded, called
  if non-null), a dispatch already bounded by cmp w24,#0x1f in BOTH builds.
  New gates in NEW, quoted at NEW VAs (all byte-verified, not artifacts):
  (a) entry range gate @0x23cc: mov w8,#0xb081; movk w8,#4,lsl#16;
      cmp x23,x8; b.lo 0x2498. BEFORE goes straight to bl 0xddec(x23,x24).
      x23 is an id/handle at entry: small values take the lookup path
      (bl 0x8d4 object factory), pointer-sized values take the direct path.
  (b) resolve-then-latch @0x2498-0x25bc: bl 0x8d4(x24,w23,1) -> object x23;
      cbz fail; validate [x23+#8] via bl 0xde74; re-validate via bl 0x1d24
      (the validator from delta 1); then ldr w8,[x23,#4]; mov w24,w0;
      cmp w0,w8; b.ls 0x25ac (fail path logs); at 0x25ac:
      str w24,[x23,#4]; bl 0x1830. I.e. the count used downstream is
      re-read, range-compared against stored state, and latched back before
      the table dispatch. BEFORE trusted the resolver return (bl 0xddec ->
      mov w24,w0) with no re-read/compare/latch of [x23+#4] on this path
      (no str [x23,#4] anywhere in BEFORE 0x23ac; the predicate 0xddec is the
      byte-identical twin of NEW 0xde74, only shifted VA).
  Callee roles (prologues + behavior, both images): 0x8d4 object factory
  (malloc 0x10, store tag byte); 0x1d24 bounds validator ([x0+#4]+8 <=
  0x4b080); 0xde74/0xddec boolean predicate over 0x1dfc; 0x1830 bounded worker
  (0x60 frame, rejects w2 > 7... entry cmp w20,#7; b.ls fail).

WHAT THIS DOES AND DOES NOT CLOSE
  Still closed: fix location for CVE-2026-21046 is the fabrickeymaster SPU
  firmware (neither the QSEE keymaster TA, byte-identical DZDP-vs-DZG1, nor
  proven in the HLOS HAL). The "blocked on input" note is still unblocked by
  the AFTER split set above.
  Corrected: the defect is the resolve/use path in 0x23ac (validated-count
  handling before the w24-keyed table dispatch), NOT the six stamp/check
  stubs, which are identical in both builds. The old QSEE-vs-SPU proximity
  table stays dropped (cross-image deltas).
  Not closed: the precise vulnerable statement (which attacker-influenced
  value was trusted at which use in BEFORE's ddec-based flow) needs the
  dataflow of [x23+#4] writers across HLOS calls; the other end of the table
  dispatch (entries at 0x105880+w24*16); the 0x1d24-fail vs 0x13858 log-call
  renumbering (0x137d0 -> 0x13858, shift only).
  Concurrency verdict: an intra-TA thread race is unlikely; the image serves
  via GPAppLib (GPAppLib_handleRequest: serialized requests) and imports no
  thread/mutex primitives (23 PLT imports: GPAppLib_*, qsee_malloc/free/kdf/
  prng/log, cmnlib, sys/open/close/write only). The TOCTOU window, if any,
  spans HLOS requests against persistent/shared objects (imported-key state?)
  or the HLOS HAL <-> SPU boundary. The HLOS side (binaries_extra/
  vendor.samsung.hardware.security.fkeymaster-service, fabric_crypto: pulled,
  never analyzed) is the next place to look, not this TA's threads.
  Ruled out along the way (shapes verified in both images, not fixes):
  8-func cluster @0x47e78-0x048378 (descriptor-table churn, no new branch);
  @0xbe8b8-0xbe938 (in-place word loop -> copy-to-0x80-stack-buffer then
  dispatch to bounds-checked SIMD/butterfly, crypto-primitive shape, no
  check-before-indirect-branch).
