PRODUCTION METHOD
  The image was read with Python 3, pyelftools 0.33 and Capstone 5.0.7.
  scripts/ta_audit.py supplied the PT_LOAD VA mapping, DT_HASH dynamic-symbol
  parsing, PLT resolution and AArch64 disassembly. Direct byte searches were

  objects were checked with OpenSSL 3.5.4:

    dd if=partitions/em.img bs=1 skip=$((0xf4df0)) count=$((0x126)) status=none \
      | openssl pkey -pubin -inform DER -text -noout
    dd if=partitions/em.img bs=1 skip=$((0xf503c)) count=$((0x126)) status=none \
      | openssl pkey -pubin -inform DER -text -noout

  This evidence was assembled from those read-only results. No device command,
  token operation, RPMB/devinfo access or firmware mutation was performed.

RESULT SUMMARY
  Confirmed:
    The current ESS request is hybrid encrypted.
    A random 32-byte AES key and random 16-byte IV encrypt the request
    plaintext with AES-256-CTR.
    A separate random 16-byte IV drives a fixed-table 16-byte-block CTR
    transform over session_iv[16] || session_key[32].
    RSA public encryption with OAEP wraps the resulting 64-byte value:

      wb_iv[16] || wb_ctr(session_iv[16] || session_key[32])[48]

    OAEP uses SHA-1, MGF1-SHA1 and an empty label.
    The RSA result is limited by the caller to at most 0x100 bytes.
    SHA-256 covers rsa_ciphertext || aes_ciphertext. It is an unkeyed digest,
    not a GCM tag or MAC.
    The wire envelope is textual and colon-delimited:

      01:R:RB:B64(RSA_CT):C:CB:B64(AES_CT):B64(SHA256(RSA_CT || AES_CT)):

    The TA keeps the generated AES key. ESS install and recovery responses use
    that key with a server-supplied IV and AES-256-CTR. No RSA private decrypt
    or unwrap path exists in the analyzed TA ESS response path.

  Likely:
    The fixed-table CTR transform is white-box AES-CTR. Its 16-byte block size,
    table selection, counter update and XOR construction are confirmed, but the
    obscured fixed key and its nominal key size are not recoverable from the
    wrapper alone.
    The operational ESS leaf key is probably RSA-2048 because the output cap is
    256 bytes and both embedded type-0x14 RSA trust anchors are RSA-2048.

  Possible:
    The current random wb_iv may be the structural descendant of the historical
    unexplained 16-byte member. Its current role is no longer unexplained: it is
    the counter IV for the fixed-table CTR layer.

  Unknown:
    The runtime leaf certificate, modulus, exponent and exact modulus length.
    Static code proves RSA and an output no larger than 256 bytes, not that every
    accepted runtime leaf is exactly RSA-2048.
    The fixed white-box key value and nominal key size.
    The final platform entropy source used by the statically linked OAEP seed
    generator. OAEP encoding does generate a fresh seed internally, but its
    platform source was not reduced to a named qsee import here.
    The semantic names of the seven opaque ESS V1 prefix fields.

TEXT ENVELOPE
  VA 0x018104..0x018294 appends each field followed by ":". Decimal formatting
  is performed before this region; binary fields are Base64-encoded.

  Definitions:
    R  = raw RSA ciphertext length, 1..256
    RB = Base64 RSA length, 4 * ceil(R / 3)
    C  = AES ciphertext length, equal to plaintext length, at most 1024
    CB = Base64 AES length, 4 * ceil(C / 3)
    H  = Base64 SHA-256, always 44 characters

  Serialized envelope:

    01:R:RB:B64(RSA_CT):C:CB:B64(AES_CT):H:

  Field table:
    index  text offset                                      size  origin
    0      0                                                2     literal "01"
    1      3                                                dR    decimal R
    2      4+dR                                             dRB   decimal RB
    3      5+dR+dRB                                         RB    Base64 RSA_CT
    4      6+dR+dRB+RB                                      dC    decimal C
    5      7+dR+dRB+RB+dC                                   dCB   decimal CB
    6      8+dR+dRB+RB+dC+dCB                               CB    Base64 AES_CT
    7      9+dR+dRB+RB+dC+dCB+CB                            44    Base64 SHA-256
    end    54+dR+dRB+RB+dC+dCB+CB                           0     after trailing ':'

  dR, dRB, dC and dCB are decimal digit counts. Every offset after field 0 is
  therefore variable. If the runtime RSA key is 2048 bits, R=256 and RB=344,
  but that runtime condition is not statically Confirmed by this image alone.

  The upper transport layer prefixes this result with "+ENGMODES:", subtype and
  ",OK,". That framing is not part of em_ess_encrypt_message itself.

PSEUDOCODE
  Names beginning with opaque_ are descriptive labels, not recovered symbols.

    int em_ess_encrypt_message(out, out_len, req, cert, cert_len) {
        if (!out || !out_len || !req || !cert)
            return error;

        if (em_get_random(G + 0x258b4, 32) != 32)
            return error;
        memcpy(req + 0xcd, G + 0x258b4, 32);

        if (em_get_random(G + 0x258a4, 16) != 16)
            return error;
        memcpy(req + 0xbd, G + 0x258a4, 16);

        if (em_crypto_aes_256_ctr_encrypt(
                G + 0x94, *(u32 *)(G + 0xc894),
                G + 0x258b4, G + 0x258a4,
                G + 0xc898, G + 0x258a0) != 0)
            return error;

        if (em_get_random(G + 0x258d4, 16) != 16)
            return error;

        if (opaque_fixed_table_ctr(
                G + 0x258a4, 48,
                G + 0x258e4, G + 0x25964,
                G + 0x258d4, 1) != 0)
            return error;

        rsa_plain = G + 0x258d4;
        rsa_plain_len = 16 + *(u32 *)(G + 0x25964); // 64
        if (em_crypto_rsa_encrypt(
                cert, cert_len, rsa_plain, rsa_plain_len,
                G + 0x25968, G + 0x25c70) != 0)
            return error;
        if (*(u32 *)(G + 0x25c70) > 0x100)
            return error;

        aggregate = G + 0x25c74;
        memcpy(aggregate, G + 0x25968, rsa_len);
        if (*(u32 *)(G + 0x258a0) > 0x400)
            return error;
        memcpy(aggregate + rsa_len, G + 0xc898, aes_len);
        sha256(aggregate, rsa_len + aes_len, G + 0x26178);

        b64_rsa = base64(G + 0x25968, rsa_len);
        b64_aes = base64(G + 0xc898, aes_len);
        b64_hash = base64(G + 0x26178, 32);

        append(out, out_len, "01", ":");
        append(out, out_len, decimal(rsa_len), ":");
        append(out, out_len, decimal(len(b64_rsa)), ":");
        append(out, out_len, b64_rsa, ":");
        append(out, out_len, decimal(aes_len), ":");
        append(out, out_len, decimal(len(b64_aes)), ":");
        append(out, out_len, b64_aes, ":");
        append(out, out_len, b64_hash, ":");
        return 0;
    }

ESS V1 INPUT FIELD CORRECTION
  This is a correction to the earlier segment count, not a crypto inference.

  The type-1 parser sets the required delimiter count to 0x0b at
  VA 0x015ff8, file 0x016ff8. Its tokenizer at VA 0x009ccc has strtok-style
  behavior and does not return a nonempty token after a trailing delimiter.
  Downstream indexing uses:

    token[count-1] as SHA-256 hex at VA 0x0162e8
    token[count-2] as certificate hex at VA 0x0165c4
    token[count-3] as certificate byte length at VA 0x016604

  The accepted serialized shape is therefore:

    01:field_0:field_1:field_2:field_3:field_4:field_5:field_6:
       cert_len:cert_hex:sha256_hex:

  It has 11 nonempty tokens and a mandatory terminal empty component created by
  the trailing colon. Counting that empty component as a field produced the old
  old segment-count description. Current code has seven nonempty
  intermediate fields. The parser's maximum-length slot 11 is zero, so a
  twelfth nonempty token is rejected; the tokenizer returns NULL rather than a
  token for the empty component after the final colon.

  Current-code field table:
    token  name        maximum text length  confirmed use
    0      version     2 in practice         exact ASCII "01"
    1      field_0     0x100                 included in verified prefix body
    2      field_1     3                     included in verified prefix body
    3      field_2     0x80                  included in verified prefix body
    4      field_3     8                     parsed/validated as numeric flag/value
    5      field_4     8                     parsed/validated as numeric flag/value
    6      field_5     0x64                  included in verified prefix body
    7      field_6     6                     included in verified prefix body
    8      cert_len    5                     decimal decoded-certificate length
    9      cert_hex    0x1000                hex DER X.509 bytes
    10     sha256_hex  0x40                  hex SHA-256, exactly 32 decoded bytes
    slot11 unused      0                     twelfth nonempty token is rejected
    end    terminator  n/a                   empty component after trailing ':'

  The parser hashes the preceding serialized body and compares all 32 decoded
  bytes with token 10. It hex-decodes token 9 and checks that token 8 equals the
  decoded byte count. It stores fields 0 through 6 as the verified prefix body,
  which em_ess_make_token_request later places at the start of its plaintext.

  No field_0 through field_6 value selects RSA, OAEP, AES, key size, IV, key id,
  certificate id or server id in the analyzed crypto path. Their semantic names
  remain Unknown. Historical labels are not evidence for this firmware.

HISTORICAL COMPARISON
  Historical description:

    RSA-2048/OAEP -> 64 bytes -> AES-256 key[32] + IV[16] + unknown[16]
    AES-256-CTR observed or suspected in older implementations

  Matches, Confirmed in the current image:
    RSA public encryption with OAEP
    exact 64-byte RSA plaintext
    explicit 32-byte AES-256 key
    explicit 16-byte payload IV
    an additional random 16-byte value
    AES-256-CTR for the ESS request payload
    RSA output capacity and check of 0x100 bytes

  Does not match exactly:
    Current 64-byte RSA plaintext is not a plain 32+16+16 concatenation.
    It is wb_iv[16] || fixed_table_ctr(session_iv[16] || key[32])[48].
    Current inner order is IV then key, not key then IV.
    The additional 16 bytes are a confirmed CTR IV for the fixed-table layer,
    not an unexplained clear metadata field.
    The runtime leaf modulus size is not embedded, so RSA-2048 remains Likely,
    not Confirmed, for the supplied ESS certificate.
    The request IV is RSA-protected and is not a separate text-envelope field.
    The current payload path has no GCM tag, CCM tag, AAD or padding.

  Newly specified detail:
    OAEP is SHA-1 with MGF1-SHA1 and empty label.
    The envelope includes an unkeyed SHA-256 over RSA_CT || AES_CT.
    The response path uses the retained AES-256 key with a server-supplied IV.
