# SVE-2026-3546: portability to the SM-S928B (e3q / SM8650)

Date: 2026-11-04
Mode: static, offline, read-only analysis. No phone was connected.
No PoC script was executed (not `flash_and_fuse.py`, not `sign_bl.py`, not
`build_loader.sh`). No partition, OTP or fuse was touched.
Target: SM-S928B (`e3q`), audited firmware `S928BXXU5DZDP`, later material
`S928BXXS6DZG1`, `S928BXXS6DZH2` and `S928BXXU6EZIF`.
PoC: `SVE-2026-3546/` (declares support for `s5e8825` only).

## Verdict

The exploit is **not portable** to the SM-S928B, and the reason is stronger
than "another platform": the component the PoC attacks does not exist in the
Qualcomm ABL Odin path.

What is reusable is the **transport**: the S24 ABL speaks the same framing
(0x400-byte frame, 8-byte reply), exports `LOKE`, answers `0x00028000` to the
`0x64/0` handshake, and implements exactly commands `0x64/0x65/0x66` with the
same subcommand map the PoC uses (`0x66` 0/5 = state, 2/6 = data, 3/7 =
finalize).

What does **not** exist in the S24 ABL is the decompression stage that
produces the primitive. In the DZDP Odin module (identical in DZG1 across the
compared windows), `0x66/5` only stores the state, `0x66/6` falls into the
**same** raw data receiver as `0x66/2`, and `0x66/7` falls into the **same**
finalizer as `0x66/3`. There is no decompressor call anywhere in the handler.
The strings `Uncompressed BlkSize > 1MB`, `BlkSize(%d) != ret(%d)`,
`mdcompress` and `zlib compression` are present in the binary but **have no
reference at all** in the whole module (full 140,288-instruction sweep with
`skipdata`, plus `adr`, 32-bit RVA and 64-bit pointer searches). They are
orphan strings.

Practical consequence: the PoC sequence is *accepted* by the S24 (no command
is rejected), but the "compressed" blocks are stored as raw data in the
300 MB XMIT buffer, which is bounded exactly. Nothing writes out of bounds,
nothing reaches the Odin callback pointer, and the `0x8825EACE` marker is
never produced.

## 1. The Exynos PoC trigger, reconstructed from the code

### 1.1 Transport and framing (confirmed)

From `SVE-2026-3546/flash_and_fuse.py`:

| Item | Value |
| --- | --- |
| USB | VID `0x04E8`, PID `0x685D`, interface 1, EP `0x01` OUT / `0x81` IN |
| Handshake | `b"ODIN"` (4 bytes) → `b"LOKE"` (4 bytes) |
| Version | `cmd(100, 0)` must return `0x00028000` |
| Command | `struct.pack("<256I", ...)` = 1024 bytes; `[0]`=op, `[1]`=sub, `[2..]`=args |
| Reply | 8 bytes `<II` = (echoed op, return value) |

### 1.2 Exact sequence (confirmed, line by line)

1. `100/0` — handshake, expects `0x28000`.
2. `100/2` args `(0x7FFFFFFF,)` — total transfer size.
3. `101/1` — PIT size, accepted in `0x1C..0x4000`.
4. `101/2` args `(index,)` + 500-byte read, repeated `ceil(size/500)` times.
   No 8-byte ack between the chunks.
5. `100/5` args `(BLOCK,)` — block size; `BLOCK` is derived from the LK
   (power of two between `0x10000` and `0x400000`, see `comp_output()`).
6. `102/0` — start of raw mode (reply ignored).
7. For each image, `put()`:
   - `102/2` args `(size,)`;
   - `ceil(size/BLOCK)*BLOCK` bytes in USB writes of `BLOCK`, with an 8-byte
     ack read after **each** block;
   - `102/3` args `(0, size, 0, blk_start, blk_count, last)`.
8. `100/5` args `(8,)` — 8-byte block for the control block.
9. `102/5` — start of compressed mode (no args).
10. Walk: `WALK_LEN/BLOCK` iterations of `put_comp(size<=BLOCK, scratch)`.
11. Final block: `put_comp(len(ctl), boot, ctl)`, which must return
    `0x8825EACE`.

`put_comp()` builds `raw = LE32(size | 0x80000000) + data`, sends `102/6`
with `len(raw)`, sends the payload in 8-byte blocks and closes with
`102/7 (0, 8, 0, blk_start, blk_count, 0)`.

Important note: every `put_comp` uses the **same** `blk_start/blk_count` pair
(the `UL_KEYS` PIT partition). The content written to the partition is
irrelevant; the useful effect is the advance of the output cursor in RAM.

### 1.3 Memory layout the PoC requires (confirmed as a requirement)

`resolve.py` does not "guess" addresses: it **rejects** the image if the
invariants do not hold. That describes the memory model the exploit needs to
find:

- `b"s5e8825\0"` must exist in the LK, otherwise it aborts (explicit guard).
- `image_map()`: requires **a single** mapping (name, start, end, phys) that
  contains the BSS; LK base = `start`.
- `input_map()`: from the `compressed_download_init` string, extracts
  `base/total/slot` (32-bit base > `0xffffffff`, i.e. a high VA).
- `parallel()`: from `parallel_download_init`, extracts `base/total/slot`;
  requires `slots >= 2` and `total == slots*slot`.
- `comp_output()`: from a pattern `ldr w8,[x8]; cmp w8,#1; add x0,x8,x20;
  bl ...`, extracts the accumulator base and the block (a power-of-two
  constant, repeated at least twice).
- `send_info()`: locates the Odin setter that stores **two adjacent
  pointers** (callback pair), the registration call and the uses
  `mov w1,#8; blr x<cb>`. Requires `0 < callback - reply <= 0x1000` and
  `bss_lo < callback < bss_hi`.
- In `main()`: requires the `in_base` mapping to be **executable**
  (`ent[4] & ((1<<53)|(1<<54)) == 0`), `slots >= 4`,
  `slots == par_slots`, `walk = write - out_base` in `(0, 2^32)`,
  `code + 0xEE0 <= code_base + 0x1000`.

In other words: the PoC depends on (a) an executable parallel staging area,
(b) the decompression output accumulator below it, (c) a reply/callback pair
in the BSS at most 4 KB above the end of the staging area.

### 1.4 The control block (confirmed)

```
ctl_len = (callback - reply) + 8
ctl[0x00 .. 0x08) = REPLY_ADDR     # qword
ctl[cb_off .. +8) = CODE_ADDR      # qword, cb_off = callback - reply
```

The overflow writes the byte image `[reply, callback+8)`; the Odin callback
then points at the code already staged in executable RAM
(`in_base + code_slot*in_slot + 0x100`). The payload restores the original
callback (`*(u64*)SEND_CALLBACK = SEND_CALLBACK_DEFAULT`), stores
`((u32*)response)[1] = 0x8825EACE` and calls `send_response(response, 8)`.
The `0x8825EACE` word coming back on `102/7` is the code-execution proof the
PoC uses.

### 1.5 Sink: what is demonstrated and what is inferred

**Confirmed (client side):** the PoC builds a compressed transfer whose
declared size (`size | 0x80000000`) is added to a global cursor per
transaction; the walk covers `write - out_base` bytes and the final block
runs past the end of the buffer up to the reply/callback pair in the BSS.

**Likely (device side):** the sink is the write of decompressed output at
`out_base + accumulated_offset`, with no validation of the total against the
buffer capacity. That is the only reading consistent with the `resolve.py`
invariants (`DECOMPRESS_ADDRESS = in_base`, `DECOMPRESS_CAPACITY = in_slot`,
`walk = write - out_base`) and with the payload (which needs arbitrary bytes
at the destination).

**Not demonstrated:** the exact sink instruction, the internal block format
(real LZMA vs. a "stored" block with a declared size) and why arbitrary
`ctl` bytes are reproduced at the destination. The S5E8825 binary is **not in
the workspace**; `resolve.py` only works with the S5E8825 BL tar, and
`offsets.py` is generated and gitignored. Without that artifact, the trigger
reconstruction stops at the protocol and invariant level.

Technical note: with `data=bytes(4)` (four zeros) the walk blocks are
consistent with a degenerate LZMA stream that produces zeros; the final block
uses the `ctl` bytes themselves as the payload. The two possible readings
(permissive LZMA with a fallback, or a "stored" block whose declared size
drives the cursor) cannot be separated without the LK.

## 2. Mapping onto the SM-S928B Odin handler

Module: `audit/decompiled/odin-oneui8.pe`, 966,656 bytes,
`.text` RVA `0x1000`, size `0x89000`; `.data` RVA `0x8a000`;
`.reloc` RVA `0xe9000`. SHA-256 recorded in the earlier audit:
`c05b772c…`; md5 `889751eeb1f05b9b0dc52dbe8f1629a8`. It is **byte-identical**
to `abl-main.pe` (same md5) — the duplicate is not independent evidence.

### 2.1 Real dispatcher (reconfirmed by disassembly)

- Entry `0xb650`; frame `sub sp, sp, #0xa40`.
- `0xb698`: `adrp x0,#0x79000; add x0,x0,#0xf8c` → the `LOKE` string
  (`0x79f8c`), `bl 0x8660`. The ABL **sends** `LOKE`; the handshake is live
  code, not a dead string.
- `0xb768`–`0xb78c`: clears 0x400 bytes at `sp+0x70`, reads exactly 0x400
  (`bl 0xe674`) and copies 0x400 to `sp+0x470` (`bl 0x4e80`).
- Fields: `+0x470` cmd, `+0x474` sub, `+0x478` arg0/size, `+0x47c` arg1.
- `0xb790`: `sub w8,w8,#0x64; cmp #6; b.hi 0xb9e8`; byte table at `0x7edc0`
  → `0x64..0x6a`. Commands and range identical to the PoC.

### 2.2 The `0x66` subcommands (this is the most important correction)

`0xb81c`:

```
0xb838  cmp w8, #7            ; sub
0xb840  b.hi 0xc87c           ; sub > 7: reject
0xb848  mov w10, #0x21        ; bits 0 and 5
0xb854  b.ne 0xbd1c           ; sub 0 or 5 -> state setter
0xb858  mov w8, #0x44         ; bits 2 and 6
0xb860  b.ne 0xbd2c           ; sub 2 or 6 -> data receive
0xb864  mov w8, #0x88         ; bits 3 and 7
0xb86c  b.eq 0xc87c           ; sub 1 or 4 -> reject
                              ; sub 3 or 7 -> 0xb870 (finalize)
```

- `0xbd1c`: `str w8,[c60a8]` (state = sub) and acks `0x66`. That is, `0x66/0`
  → state 0; `0x66/5` → state 5.
- `0xbd2c`: requires state ∈ {0,5} (`0xbd44`–`0xbd4c`, otherwise `0xc34c`);
  stores `c6090 = (state == 0)` at `0xbd5c`; checks `arg1 < 0x20000001`
  (`0xbd68`–`0xbd78`); initializes (`bl 0xe75c`); reads the chunk from
  `0x8d3c4`; `tbnz bit31` rejects; computes `w23 = chunk` (or `arg0` if
  `offset+chunk > 0x6400000`); and performs the USB read through `blr x8` at
  `0xbde0` into `[c6198] + offset + [c618c+0xcc]`.
- `0xb870`: requires state ∈ {0,5}; `arg1 < 0x20000001`; `arg0 == 1` →
  `0xc5d0`, `arg0 == 0` → `0xc5dc`, otherwise → `0xc818`. At `0xc5dc` it
  reads `u32` at `packet+0x18` and `u32` at `packet+0x1c..+0x1f` and stores
  them in `c60ac/c60b0`; `0xc6bc` treats `c60ac` as a partition id (range
  `0x46..0x6d`); worker `0xa9e0` calls `0x58350` (per-state verification).

**No decompressor exists on any of these paths.** The indirect calls inside
`0xb81c..0xc9c0` are only:

| Site | Target |
| --- | --- |
| `0xb9a8` | the `0x67` image-commit loop |
| `0xbde0` | USB read (protocol) into the 300 MB buffer |
| `0xbe00` | USB protocol write / second stage |
| `0xc3c4` | `LocateProtocol` / UEFI protocol with GUID `0x89bf8` |
| `0xc938` | protocol call (`[x0+8]`) on the verification path |

### 2.3 Handshake: compatible, but dependent on a flag

`0xc558`/`0xc5b4`:

```
0xc558  mov w19, #0x20000
0xc5b4  orr w9, w19, #0x8000      ; 0x28000
0xc5bc  ldr w8, [c6090]
0xc5c0  cmp w8, #0
0xc5c4  csel w1, w9, w19, eq      ; c6090 == 0 -> 0x28000
0xc5c8  mov w0, w21               ; 0x64
```

`c6090` is initialized to **0** in the file (offset `0xc6090` = `00000000`),
is written **only** at `0xbd58` (`state == 0`) and read **only** at `0xc5bc`.
So the handshake returns `0x28000` on a clean boot — the value the PoC
expects — and starts returning `0x20000` after a raw XMIT in state 0. This
alone shows the S24 state machine is not the Exynos LK one, only similar.

### 2.4 Bounds of the raw path (confirmed)

- `0x64/5` stores the chunk at `0x8d3c4` after `cmp #0x100, lsl #12`
  (`0xc18c`): **≤ 1 MiB**.
- `0x66/2|6`: `arg1 < 0x20000001` and `offset + chunk ≤ 0x6400000` (100 MiB).
- `0xa354`–`0xa36c`: allocates `0x12c00000` (300 MiB) through the protocol,
  with the descriptor at `sp+0x18`; `0xa3c0`–`0xa3e0` stores the base pointer
  in `[c6198]` (the destination pointer read at `0xc4f0`, `0xc510` and
  `0xd068`). `0xa370`–`0xa37c` obtains `0x3fc00000` (1020 MiB) and stores it
  in `[c61a0]`. Small correction to the earlier audit: the store at `0xa37c`
  is to `c61a0` (`0xc6000+0x1a0`), not `c6198`; the 300 MiB pool reaches
  `c6198` through `0xa3e0` (`[c6070+0x128]`).
- `0xcad8`: adds `0x6400000` to the rotation and resets it when the counter
  reaches 3 → maximum range `3 × 100 MiB = 300 MiB`, exactly the allocation
  size; last valid byte `0x12bfffff`.
- The PIT path (`0x65/1..3`) caps at 0x8000 and writes only after the
  verification at `0x63630`.

### 2.5 Decompression strings: present and orphaned (confirmed)

| String | VA | References found |
| --- | --- | --- |
| `mdcompress` | `0x92978` (`.data`) | none |
| `zlib compression` | `0x7798d` | none (there is a qword at `0x95008`, but in a region that is not a pointer table) |
| `Uncompressed BlkSize > 1MB` | `0x76c83` | none |
| `BlkSize(%d) != ret(%d)` | `0x760ed` | none |
| `Odin : Xmit Completed after final(%d)` | `0x775e2` | `0xc01c` (positive control for the method) |

Method: full linear disassembly of `.text` with `md.skipdata=True`
(140,288 instructions; without `skipdata` the sweep stops at `0x456fc`),
`adrp`+`add`/`adr` searches for the VAs, 32-bit RVA and 64-bit pointer
searches across the whole file. The positive control (`0x775e2` → `0xc01c`)
proves the resolution works; the absence of the others is a result, not a
tool failure.

The same strings are still present in the `EZIF` FV (One UI 9), meaning the
legacy compression code is still linked — but the Odin module of that build
was not extracted to repeat the xref sweep (recorded gap).

### 2.6 Code origin (strong evidence it is another product)

`0x74825` holds the build path:

```
.../bootable/bootloader/edk2/QcomModulePkg/Library/Sec_Secure/Sec_Auth_Odin.c
```

The S24 Odin is an EDK2 `QcomModulePkg` module, not the Exynos LK Odin. That
explains why the protocol name and command numbers match (it is the same wire
protocol) without the implementation being the same.

### 2.7 Stability across builds

Byte-for-byte comparison with `odin-oneui8-dzg1.pe`:

| Window | Differences |
| --- | --- |
| `0xb81c..0xb8d0` (`0x66` dispatch) | 0 / 180 |
| `0xbd2c..0xbdf0` (data receive) | 0 / 196 |
| `0x58350..0x58430` (per-state verification) | 0 / 224 |

This confirms and extends the earlier audit's spot check to the windows that
matter here.

## 4. Reusable, requiring reimplementation, and what is missing

**Reusable (with small adaptation):**

- The USB client: device open, `ODIN`/`LOKE` magic, 0x400-byte frame, 8-byte
  reply read, `100/0`, `100/2`, `101/1`, `101/2`, `100/5`, `102/0`, `102/2`,
  `102/3`.
- The PIT loop and the size check (`0x1C..0x4000`).
- The idea of "walking" a cursor across successive transactions.

**Would require reimplementation:**

- The whole trigger: on the S24 one must find *another* consumer of a declared
  size. The PoC's compressed block is not interpreted as compressed.
- The whole payload stage: addresses, memory map, executable area,
  reply/callback pair, OTP `smc`, signing format.
- The arg semantics of `0x66/3` and `0x66/7` (the S24 reads `packet+0x18` and
  `packet+0x1c`, not `dst0/dst1/last`).

**Data/binaries missing to close the conclusion:**

1. S5E8825 `sboot.bin`/`lk.bin` (or the generated `offsets.py`) — without it
   the PoC sink stays at the invariant level.
2. The official S5E8825 BL used by the author — to date the bug relative to
   SMR Nov-2026 Release 1.
3. **Post-fix SM-S928B BL (SMR Nov-2026 Release 1)** — this is the artifact
   that decides real applicability.
4. The `EZIF` `odin` extracted as a PE, to repeat the xref sweep on the newest
   build.
5. The SM-S928B PIT (not in the repository) — only needed for a full protocol
   replay, not for the verdict.
6. The real Odin client (Odin3/Smart Switch) to map the `0x66/3` and `0x66/7`
   args without inference.

## 5. Separate assessments

| Question | Answer | Basis |
| --- | --- | --- |
| Transport portability | **Partial, confirmed at the framing level** | `0xb698`, `0xb768`, `0xb790`, `0xc5b4`; PID/intf unverified |
| Trigger portability | **No** | `0x66/6` lands at `0xbd2c` (same path as `0x66/2`); no decompressor in `0xb81c..0xc9c0`; orphan strings |
| Primitive portability | **Not in this component** | 300 MiB buffer with exact wrap (`0xa354`, `0xcad8`); no unbounded cursor |
| Code execution on the S24 | **Not demonstrated** | no out-of-bounds write; the only pre-verification deviation is a 0x100 B OOB read |
| Change to the unlock/AVB decision | **None** | the bulletin promises an OOB write, not control; the S24 `devinfo`/AVB audit is unchanged |

On unlock: even if a pre-AVB primitive existed, it could in principle bypass
the `SetUnlocked`/`IsUnlocked` path. But nothing here demonstrates controlled
writes, pre-AVB execution, or reach into `devinfo+0x0d`. The earlier verdict
(`LIKELY NO`) stands.

## 8. Most informative next step

**Obtain the SM-S928B BL from SMR Nov-2026 Release 1 (or later) and diff the
Odin module against DZG1/EZIF.** If the November patch touches
`odin-oneui8.pe`, the changed function points at the component and resolves
applicability in 1–2 days. If it does not, SVE-2026-3546 is probably not the
Qualcomm ABL Odin (or the target is XBL/`uefisecapp`), and the S24 leaves the
scope with evidence rather than by assumption.

None of the three is a demonstrated bug today; any of them would be
